ผลลัพธ์การเรียนรู้​

เมื่อทำ tutorial นี้เสร็จแล้ว คุณคาดว่าจะเข้าใจสิ่งต่อไปนี้:

  • เหตุใดคุณสมบัติที่ QPU รายงานจึงอาจล้าหลังพฤติกรรมปัจจุบันของอุปกรณ์ และเมื่อใดที่คุ้มค่าที่จะวัดใหม่ด้วยตัวเอง

  • การทดลอง characterization มาตรฐานทั้งห้าแบบ (readout, single-qubit randomized benchmarking, layered two-qubit randomized benchmarking, T1T_1T1​ และ T2T_2T2​) แต่ละแบบวัดอะไร

  • วิธีรัน characterization suite ทั้งหมดในการเรียกครั้งเดียวหรือทีละขั้นตอน และรับออบเจ็กต์ backend ที่มีคุณสมบัติที่รีเฟรชแล้วกลับมา

  • วิธีเปรียบเทียบคุณสมบัติที่วัดได้กับคุณสมบัติที่รายงาน และเหตุใดความแตกต่างบางอย่างจึงสะท้อนถึงวิธีการวัดมากกว่าการ drift ของอุปกรณ์

ข้อกำหนดเบื้องต้น​

ขอแนะนำให้คุณทำความคุ้นเคยกับหัวข้อเหล่านี้:

  • เวิร์กโฟลว์ Qiskit patterns

  • โหมดการรัน Qiskit Runtime โดยเฉพาะ batch mode

  • วิธีสำรวจ ข้อมูล QPU เช่น คุณสมบัติของ backend และข้อมูลการ calibration

ความเป็นมา​

IBM Quantum® QPU ทุกตัวรายงานชุดคุณสมบัติที่อธิบายว่าคิวบิตแต่ละตัวทำงานได้ดีเพียงใดในปัจจุบัน: เวลา relaxation (T1T_1T1​), เวลา coherence (T2T_2T2​), readout error, และ error ของ gate หนึ่งและสองคิวบิต ตัวเลขเหล่านี้มีความสำคัญในทางปฏิบัติ transpiler ใช้ตัวเลขเหล่านี้เพื่อตัดสินใจว่าคิวบิตทางกายภาพใดที่ Circuit ของคุณควรรัน เทคนิคการลด error อาศัยตัวเลขเหล่านี้ และคุณอาจใช้ตัวเลขเหล่านี้เพื่อตัดสินว่าอุปกรณ์ทำงานได้ดีเพียงพอสำหรับการทดลองหรือไม่

คุณสมบัติที่รายงานมาจากกระบวนการ calibration ซึ่งโดยทั่วไปจะรันประมาณวันละครั้ง อย่างไรก็ตาม คิวบิตแบบตัวนำยิ่งยวดสามารถ drift ได้ในช่วงเวลาที่สั้นกว่า และข้อบกพร่องชั่วคราว (ที่เรียกว่า two-level system) สามารถทำให้คิวบิตที่ดูดีเยี่ยมในเวลา calibration เสื่อมสภาพลงชั่วคราวได้ นอกจากนี้ job มักจะถูก transpile ไว้ก่อนที่จะรันจริงนานพอสมควร ดังนั้นการตัดสินใจที่อิงจากคุณสมบัติที่รายงานอาจตั้งอยู่บนข้อมูลที่ล้าสมัย tutorial การ benchmark แบบ real-time สำหรับการเลือกคิวบิต แสดงให้เห็นว่าคุณสมบัติเหล่านี้สามารถผันผวนได้มากเพียงใดในแต่ละวัน และสร้างเวิร์กโฟลว์ characterization แบบเต็มด้วยมือจาก Qiskit Experiments แต่ละตัว

tutorial นี้แสดงเวอร์ชันที่คล่องตัวของเวิร์กโฟลว์นั้น โดยใช้ยูทิลิตี้ BackendCharacterization จาก Qiskit Device Benchmarking ซึ่งรวมการสร้างการทดลอง, การส่ง job, และการ fit เส้นโค้งไว้ในการเรียกไม่กี่ครั้ง คุณใช้เวลา QPU ประมาณ 70 วินาที และได้ออบเจ็กต์ backend ที่มีคุณสมบัติสะท้อนอุปกรณ์ ในขณะนี้ พร้อมที่จะเปรียบเทียบกับค่าที่รายงาน หรือส่งต่อไปยังเครื่องมือขั้นถัดไป

การทดลอง characterization​

suite นี้วัดคุณสมบัติห้าอย่าง แต่ละอย่างมีการทดลองมาตรฐาน:

  • Readout error (readout): คิวบิตแต่ละตัวถูกเตรียมใน ∣0⟩|0\rangle∣0⟩ หรือ ∣1⟩|1\rangle∣1⟩ และวัดทันที ความน่าจะเป็นของการอ่าน state ผิดให้ error ของ state preparation and measurement (SPAM)

  • Error ของ gate หนึ่งคิวบิต (rb_1q): Randomized benchmarking (RB) รันลำดับของ single-qubit Clifford gate แบบสุ่มที่ในอุดมคติจะรวมกันเป็น identity วิธีที่ความน่าจะเป็นในการอยู่รอดสลายตัวไปตามความยาวของลำดับให้ error เฉลี่ยต่อ gate โดยไม่ขึ้นกับ error ของ SPAM

  • ความผิดพลาดของ Gate สองคิวบิต (rb_2q): แนวคิด RB แบบเดียวกันที่นำไปใช้กับเลเยอร์ทั้งหมดของ Gate สองคิวบิตที่ไม่ทับซ้อนกันซึ่งรันพร้อมกัน เหมือนกับการทดลอง layer fidelity เนื่องจากมี Gate จำนวนมากรันพร้อมกัน อัตราความผิดพลาดที่ได้จึงรวมผลของ crosstalk และใกล้เคียงกับสิ่งที่ Circuit ที่ลึกจะเจอจริง ๆ มากกว่า

  • T1T_1T1​ (t1): แต่ละคิวบิตจะถูกกระตุ้นและวัดหลังจากดีเลย์ที่เพิ่มขึ้นเรื่อย ๆ การสลายตัวของสัดส่วนสถานะกระตุ้นให้ค่าเวลาผ่อนคลาย (relaxation time)

  • T2T_2T2​ (t2): การทดลอง Hahn echo จะทำให้แต่ละคิวบิตอยู่ในสถานะซ้อนทับ (superposition) ใช้พัลส์ echo ที่กึ่งกลางของดีเลย์ และวัดว่าความเชื่อมโยงเฟส (phase coherence) หายไปเร็วแค่ไหน โดยค่าเริ่มต้นจะใช้ echo เดียว ส่วนแบบหลาย echo (แบบ CPMG) จะสาธิตในตอนท้ายของบทเรียนนี้

สิ่งที่การรีเฟรชทำและไม่ทำ​

จำสามประเด็นนี้ไว้เมื่อใช้เวิร์กโฟลว์นี้:

  • คุณสมบัติที่รีเฟรชแล้วจะอยู่เฉพาะใน backend object ที่ส่งคืนให้คุณเท่านั้น ไม่มีอะไรเปลี่ยนแปลงบนอุปกรณ์เองหรือในข้อมูลการปรับเทียบ (calibration) ที่ IBM Quantum รายงานให้ผู้ใช้คนอื่น

  • ค่าที่วัดได้เป็นภาพรวม (snapshot) ที่ถ่ายด้วยวิธีการเฉพาะ ค่าบางส่วน โดยเฉพาะความผิดพลาดของ Gate สองคิวบิตแบบเลเยอร์และค่า T2T_2T2​ แบบ single-echo ที่วัดพร้อมกัน จะถูกวัดด้วยวิธีที่ต่างจากข้อมูลการปรับเทียบที่รายงานไว้ ดังนั้นส่วนหนึ่งของช่องว่างที่คุณสังเกตเห็นจึงเกิดจากวิธีการมากกว่าการดริฟต์ บทเรียนนี้จะชี้ให้เห็นว่าจุดไหนที่เป็นเช่นนั้น

  • การจำแนกคุณลักษณะ (characterization) เองก็ใช้เวลา QPU (ประมาณ 70 วินาทีสำหรับชุดเต็มบนโปรเซสเซอร์ Heron r2) ซึ่งเป็นราคาที่ต้องจ่ายเพื่อให้ได้ข้อมูลที่ทันสมัย

เวิร์กโฟลว์นี้เป็นไปตามสี่ขั้นตอนของ Qiskit pattern:

  • ขั้นตอนที่ 1: แมปอินพุตแบบคลาสสิกให้เป็นปัญหาควอนตัม เลือกอุปกรณ์และชุดคุณสมบัติที่จะวัด

  • ขั้นตอนที่ 2: ปรับปัญหาให้เหมาะกับการรันบนฮาร์ดแวร์ควอนตัม ยูทิลิตี้นี้สร้าง Circuit การทดลองโดยตรงด้วย Gate ดั้งเดิมของอุปกรณ์ และรันแบบขนานทั่วทั้งชิป

  • ขั้นตอนที่ 3: รันโดยใช้ Qiskit primitives การทดลองรันเป็นงาน Sampler ภายใน batch

  • ขั้นตอนที่ 4: ประมวลผลต่อและส่งคืนผลลัพธ์ในรูปแบบคลาสสิกที่ต้องการ ฟิตข้อมูลการวัดให้เป็นแผนที่ความผิดพลาดต่อคิวบิต รีเฟรช Backend และเปรียบเทียบคุณสมบัติที่วัดได้กับค่าที่รายงานไว้

ตัวอย่าง Simulator ขนาดเล็ก​

บทเรียนนี้ไม่มีตัวอย่าง Simulator เวิร์กโฟลว์นี้วัดความไม่สมบูรณ์ทางกายภาพของอุปกรณ์เฉพาะเครื่องหนึ่ง เช่น คิวบิตของมันผ่อนคลายและเสียเฟสเร็วแค่ไหน และ Gate กับการอ่านค่า (readout) ของมันล้มเหลวบ่อยแค่ไหน Simulator ในอุดมคติไม่มีความไม่สมบูรณ์เหล่านี้เลย จึงไม่มีอะไรให้จำแนกคุณลักษณะ คุณสามารถแนบโมเดลสัญญาณรบกวนสังเคราะห์ไปกับ fake backend ได้ แต่การทดลองก็จะได้ตัวเลขที่คุณใส่เข้าไปเองกลับคืนมาเท่านั้น ด้วยเหตุนี้ เราจึงไปที่ฮาร์ดแวร์โดยตรง แบ่งเป็นสี่ขั้นตอนของ Qiskit pattern

ตัวอย่างฮาร์ดแวร์ขนาดใหญ่​

ขั้นตอนที่ 1: แมปอินพุตแบบคลาสสิกให้เป็นปัญหาควอนตัม​

ในเวิร์กโฟลว์นี้ "ปัญหา" คือตัวอุปกรณ์เอง อินพุตแบบคลาสสิกคือ QPU ที่คุณต้องการจำแนกคุณลักษณะและรายการคุณสมบัติที่จะวัด ส่วนการทดลองควอนตัมคือ Circuit การจำแนกคุณลักษณะที่สร้างขึ้นจากอินพุตเหล่านั้น

ขั้นแรก เลือก Backend บทเรียนนี้ใช้ ibm_kingston ซึ่งเป็นโปรเซสเซอร์ Heron r2 ขนาด 156 คิวบิต คุณสามารถใช้อุปกรณ์ IBM Quantum อื่นใดที่คุณมีสิทธิ์เข้าถึงแทนได้ (หรือเลือกด้วย service.least_busy())

service = QiskitRuntimeService()
device = "ibm_kingston"
backend = service.backend(device)

ถัดไป เลือกคุณสมบัติที่จะวัด คุณสามารถส่งชุดย่อยใด ๆ ของการทดลองต่อไปนี้ได้:

  • readout: การทดลอง SPAM (state preparation and measurement)

  • rb_1q: randomized benchmarking แบบคิวบิตเดี่ยวที่แยกอิสระ

  • rb_2q: randomized benchmarking แบบสองคิวบิตที่รันพร้อมกัน จากการทดลอง layer fidelity

  • t2: การทดลอง T2T_2T2​ Hahn echo (ใช้ echo เดียวโดยค่าเริ่มต้น)

  • t1: การทดลอง T1T_1T1​ relaxation

รันชุดเต็มเพื่อให้ได้ภาพรวมที่สมบูรณ์ของอุปกรณ์ ตัดรายการออกได้หากคุณสนใจเฉพาะบางคุณสมบัติและต้องการประหยัดเวลา QPU

experiments = ["readout", "rb_1q", "rb_2q", "t1", "t2"]

ขั้นตอนที่ 2: ปรับปัญหาให้เหมาะกับการรันบนฮาร์ดแวร์ควอนตัม​

ในบทเรียนส่วนใหญ่ นี่คือจุดที่คุณจะทำการ transpile Circuit ของคุณ แต่ในที่นี้ BackendCharacterization จะจัดการเรื่องนั้นให้ภายในตัวมันเอง มันสร้าง Circuit การทดลองโดยตรงด้วย Gate ดั้งเดิมของอุปกรณ์ รันการทดลองคิวบิตเดี่ยวบนคิวบิตทั้งหมดพร้อมกัน และจัดตารางการเบนช์มาร์กสองคิวบิตทั่วเลเยอร์ที่ไม่ทับซ้อนกันของ coupling map เพื่อให้ครอบคลุมทั้งอุปกรณ์ด้วยงานเพียงไม่กี่งาน เนื่องจากการรันแบบขนานนี้ ชุดทั้งหมดจึงใช้เวลา QPU เพียงประมาณ 70 วินาที

เริ่มต้นคลาสที่จัดการเวิร์กโฟลว์:

เมท็อด analyze_results จะรอให้งานเสร็จสิ้นและฟิตข้อมูลการวัด ได้แก่ การสลายตัวแบบเอ็กซ์โพเนนเชียลสำหรับ T1T_1T1​ และ T2T_2T2​ การสลายตัวของความน่าจะเป็นในการอยู่รอด (survival probability) สำหรับการทดลอง RB และเมทริกซ์การกำหนด (assignment matrix) สำหรับ readout มันคืนค่าดิกชันนารีของ error maps หนึ่งรายการต่อคุณสมบัติที่วัด แต่ละรายการแมปคิวบิต (หรือคู่คิวบิต) ไปยังค่าที่วัดได้

plot_characterization_comparison(

พล็อตเหล่านี้ต้องอ่านอย่างระมัดระวัง เพราะไม่ใช่ทุกช่องว่างระหว่างเส้นโค้งทั้งสองจะหมายความว่าอุปกรณ์ดริฟต์ไป:

  • ความผิดพลาดของ Readout และคิวบิตเดี่ยว: ค่าที่วัดได้ใกล้เคียงกับค่าที่รายงานสำหรับคิวบิตส่วนใหญ่ ในขณะที่ค่าที่รายงานของคิวบิตไม่กี่ตัวอยู่ห่างจากเส้นโค้งที่วัดได้มาก ความไม่ตรงกันเฉพาะจุดเหล่านี้คือการดริฟต์ที่เวิร์กโฟลว์นี้ถูกออกแบบมาเพื่อจับ

  • T1T_1T1​: ชุดข้อมูลทั้งสองกระจายตัวรอบกันโดยไม่มีการเบี่ยงเบนอย่างเป็นระบบ ซึ่งสอดคล้องกับการที่ T1T_1T1​ ผันผวนตามธรรมชาติเมื่อเวลาผ่านไป

  • ความผิดพลาดของ Gate สองคิวบิต: ค่าที่วัดได้อยู่สูงกว่าค่าที่รายงานอย่างเป็นระบบ นี่เป็นสิ่งที่คาดไว้ เพราะค่าที่รายงานวัดจาก Gate ที่แยกอิสระ ในขณะที่การทดลอง layer fidelity รัน Gate จำนวนมากพร้อมกัน จึงรวมผลของ crosstalk ด้วย ตัวเลขแบบเลเยอร์เกี่ยวข้องมากกว่ากับ Circuit ที่ลึก แต่ไม่สามารถเทียบกับข้อมูลการปรับเทียบที่รายงานได้โดยตรง

  • T2T_2T2​: ค่าที่วัดได้อยู่ต่ำกว่าค่าที่รายงานอย่างชัดเจนสำหรับคิวบิตส่วนใหญ่ อีกครั้งที่วิธีการมีบทบาทสำคัญ ดังที่จะพิจารณาในหัวข้อถัดไป

ตรวจสอบผลการทดลองแต่ละรายการ​

คุณยังสามารถตรวจสอบผลลัพธ์ดิบของการทดลองจำแนกคุณลักษณะแต่ละรายการได้ผ่านคุณสมบัติ experiment_data ซึ่งคืนค่าออบเจกต์ ExperimentData ของ Qiskit Experiments ที่อยู่เบื้องหลัง ตัวอย่างเช่น ด้านล่างนี้แสดงเส้นโค้งการสลายตัวของ T1T_1T1​ ที่วัดได้ของคิวบิตเดี่ยว ซึ่งมีประโยชน์สำหรับตรวจสอบคุณภาพของการฟิตก่อนที่จะเชื่อถือตัวเลขที่ได้

วัด T2 ด้วยชุดพัลส์ dynamical decoupling​

โดยค่าเริ่มต้น การทดลอง T2T_2T2​ จะใช้ Hahn echo เดียวและวัดคิวบิตทั้งหมดพร้อมกัน ซึ่งจากพล็อตเปรียบเทียบด้านบนแสดงให้เห็นว่าอาจให้ค่า T2T_2T2​ ต่ำกว่าที่ Backend รายงานอย่างเห็นได้ชัด สมมติฐานหนึ่งคือจำนวน echo ค่าที่รายงานอาจถูกปรับเทียบด้วย dynamical decoupling ซึ่งช่วยกดสัญญาณรบกวนความถี่ต่ำ เพื่อทดสอบสิ่งนี้ ให้รันการจำแนกคุณลักษณะเฉพาะ T2T_2T2​ โดยตั้งค่า t2_num_echoes ให้มีค่ามากขึ้น ซึ่งจะใช้ชุดพัลส์ echo แบบ CPMG ดีเลย์แทนเวลาวิวัฒนาการอิสระทั้งหมดในทั้งสองกรณี ดังนั้นค่า T2T_2T2​ ที่ฟิตได้จึงสามารถเทียบกับผลลัพธ์แบบ single-echo ได้โดยตรง
