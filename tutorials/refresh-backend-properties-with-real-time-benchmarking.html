ผลลัพธ์การเรียนรู้​

  • เหตุใดคุณสมบัติที่ QPU รายงานจึงอาจแตกต่างจากพฤติกรรมปัจจุบันของอุปกรณ์ และเมื่อใดที่ควรวัดใหม่ด้วยตัวเอง

  • การทดลองการจำแนกคุณลักษณะมาตรฐานทั้งห้าแบบ (readout, single-qubit randomized benchmarking, layered two-qubit randomized benchmarking, T1T_1T1​ และ T2T_2T2​) แต่ละแบบวัดอะไร

  • วิธีรันชุดการจำแนกคุณลักษณะทั้งหมดในการเรียกครั้งเดียวหรือทีละขั้นตอน และรับออบเจ็กต์ backend ที่มีคุณสมบัติที่รีเฟรชแล้ว

  • วิธีเปรียบเทียบคุณสมบัติที่วัดได้กับคุณสมบัติที่รายงาน และเหตุใดความแตกต่างบางอย่างจึงสะท้อนถึงวิธีการวัดมากกว่าการดริฟต์ของอุปกรณ์

  • วิธีใช้คุณสมบัติที่รีเฟรชแล้วเพื่อเลือกคิวบิต และวิธีตรวจสอบว่าคุณสมบัติเหล่านั้นช่วยปรับปรุงผลลัพธ์ของ circuit สถานะ GHZ หรือไม่

ความเป็นมา​

IBM Quantum® QPU ทุกตัวรายงานชุดคุณสมบัติที่อธิบายประสิทธิภาพปัจจุบันของคิวบิตแต่ละตัว: เวลา relaxation (T1T_1T1​), เวลา coherence (T2T_2T2​), ความผิดพลาดของ readout, และความผิดพลาดของ gate หนึ่งและสองคิวบิต ตัวเลขเหล่านี้มีความสำคัญในทางปฏิบัติ transpiler ใช้ตัวเลขเหล่านี้เพื่อเลือกคิวบิตทางกายภาพสำหรับ Circuit ของคุณ เทคนิคการลดความผิดพลาดอาศัยตัวเลขเหล่านี้ และคุณอาจใช้ตัวเลขเหล่านี้เพื่อตัดสินว่าอุปกรณ์ทำงานได้ดีเพียงพอสำหรับการทดลองหรือไม่

คุณสมบัติที่รายงานมาจากกระบวนการปรับเทียบ ซึ่งโดยทั่วไปจะรันประมาณวันละครั้ง อย่างไรก็ตาม คิวบิตแบบตัวนำยิ่งยวดสามารถดริฟต์ได้ในช่วงเวลาที่สั้นกว่า และข้อบกพร่องชั่วคราว (ที่เรียกว่า two-level system) สามารถทำให้คิวบิตที่ทำงานได้ดีในเวลาปรับเทียบเสื่อมสภาพลงชั่วคราวได้ นอกจากนี้ คุณมักจะ transpile job ไว้ก่อนที่จะรันจริงนานพอสมควร ดังนั้นการตัดสินใจที่อิงจากคุณสมบัติที่รายงานอาจขึ้นอยู่กับข้อมูลที่ล้าสมัย

บทเรียนนี้ใช้ยูทิลิตี้ BackendCharacterization จาก Qiskit Device Benchmarking ซึ่งรวมการสร้างการทดลอง การส่ง job และการ fit เส้นโค้งไว้ในการเรียกไม่กี่ครั้ง ด้วยเวลา QPU ประมาณ 70 วินาที คุณจะได้ออบเจ็กต์ backend ที่มีคุณสมบัติสะท้อนสถานะปัจจุบันของอุปกรณ์ คุณสามารถเปรียบเทียบคุณสมบัติเหล่านี้กับค่าที่รายงาน หรือส่ง backend ไปยังเครื่องมืออื่นได้ ตัวอย่างสุดท้ายใช้ค่าที่รีเฟรชแล้วเพื่อเลือกคิวบิตจริงสำหรับ circuit สถานะ GHZ และเปรียบเทียบผลลัพธ์กับ circuit เดียวกันที่คอมไพล์ด้วยคุณสมบัติที่รายงาน

การทดลองการจำแนกคุณลักษณะ​

suite นี้วัดคุณสมบัติห้าอย่าง แต่ละอย่างมีการทดลองมาตรฐาน:

  • ความผิดพลาดของ Readout (readout): การทดลองเตรียมคิวบิตแต่ละตัวใน ∣0⟩|0\rangle∣0⟩ หรือ ∣1⟩|1\rangle∣1⟩ แล้ววัดทันที ความน่าจะเป็นของการอ่านผิดให้ความผิดพลาดของ state preparation and measurement (SPAM)

  • ความผิดพลาดของ Gate หนึ่งคิวบิต (rb_1q): Randomized benchmarking (RB) รันลำดับของ single-qubit Clifford gate แบบสุ่มที่ในอุดมคติจะรวมกันเป็น identity การสลายตัวของความน่าจะเป็นในการอยู่รอดตามความยาวของลำดับให้ค่าความผิดพลาดเฉลี่ยต่อ gate โดยไม่ขึ้นกับความผิดพลาดของ SPAM

  • ความผิดพลาดของ Gate สองคิวบิต (rb_2q): การทดลองนี้ใช้วิธี RB เดียวกันกับเลเยอร์ทั้งหมดของ Gate สองคิวบิตที่ไม่ทับซ้อนกันซึ่งรันพร้อมกัน เหมือนกับการทดลอง layer fidelity เนื่องจากมี Gate จำนวนมากรันพร้อมกัน อัตราความผิดพลาดที่ได้จึงรวมผลของ crosstalk และใกล้เคียงกับอัตราความผิดพลาดใน Circuit ที่ลึกมากกว่า

  • T1T_1T1​ (t1): การทดลองกระตุ้นคิวบิตแต่ละตัวและวัดหลังจากดีเลย์ที่เพิ่มขึ้นเรื่อยๆ การสลายตัวของสัดส่วนสถานะกระตุ้นให้ค่าเวลาผ่อนคลาย (relaxation time)

  • T2T_2T2​ (t2): การทดลอง Hahn echo จะทำให้แต่ละคิวบิตอยู่ในสถานะซ้อนทับ (superposition) ใช้พัลส์ echo ที่กึ่งกลางของดีเลย์ และวัดว่าคิวบิตสูญเสียความคงสภาพของเฟส (phase coherence) เร็วแค่ไหน โดยค่าเริ่มต้นการทดลองจะใช้ echo เดียว ส่วนในบทเรียนนี้จะสาธิตแบบหลาย echo (แบบ CPMG) ในหัวข้อหลังจากนี้

ขอบเขตและข้อจำกัดของคุณสมบัติที่รีเฟรชแล้ว​

โปรดจำประเด็นต่อไปนี้ไว้เมื่อใช้เวิร์กโฟลว์นี้:

  • คุณสมบัติที่รีเฟรชแล้วจะมีอยู่เฉพาะใน backend object ที่ยูทิลิตี้ส่งคืนให้คุณเท่านั้น ไม่มีอะไรเปลี่ยนแปลงบนอุปกรณ์เองหรือในข้อมูลการปรับเทียบ (calibration) ที่ IBM Quantum รายงานให้ผู้ใช้คนอื่น

  • ค่าที่วัดได้เป็นภาพรวม (snapshot) ที่ถ่ายด้วยวิธีการเฉพาะ ค่าบางส่วน โดยเฉพาะความผิดพลาดของ Gate สองคิวบิตแบบเลเยอร์และค่า T2T_2T2​ แบบ single-echo ที่วัดพร้อมกัน จะถูกวัดด้วยวิธีที่ต่างจากข้อมูลการปรับเทียบที่รายงานไว้ ดังนั้นส่วนหนึ่งของช่องว่างที่คุณสังเกตเห็นจึงมาจากวิธีการมากกว่าการดริฟต์ บทเรียนนี้จะชี้ให้เห็นว่ากรณีเหล่านี้อยู่ตรงไหน

  • การจำแนกลักษณะ (characterization) เองก็ใช้เวลา QPU (ประมาณ 70 วินาทีสำหรับชุดเต็มบนโปรเซสเซอร์ Heron 156 คิวบิต) ซึ่งเป็นต้นทุนของข้อมูลที่เป็นปัจจุบัน

เวิร์กโฟลว์นี้เป็นไปตามสี่ขั้นตอนของ Qiskit pattern:

  • ขั้นตอนที่ 1: แมปอินพุตแบบคลาสสิกให้เป็นปัญหาควอนตัม เลือกอุปกรณ์และชุดคุณสมบัติที่จะวัด

  • ขั้นตอนที่ 2: ปรับปัญหาให้เหมาะกับการรันบนฮาร์ดแวร์ควอนตัม ยูทิลิตี้นี้สร้าง Circuit การทดลองโดยตรงด้วย Gate ดั้งเดิมของอุปกรณ์ และรันแบบขนานทั่วทั้งอุปกรณ์

  • ขั้นตอนที่ 3: รันโดยใช้ Qiskit primitives การทดลองรันเป็นงาน Sampler ภายใน batch

  • ขั้นตอนที่ 4: ประมวลผลต่อและส่งคืนผลลัพธ์ในรูปแบบคลาสสิกที่ต้องการ ฟิตข้อมูลการวัดให้เป็นแผนที่ความผิดพลาดต่อคิวบิต รีเฟรช Backend และเปรียบเทียบคุณสมบัติที่วัดได้กับค่าที่รายงานไว้

ตัวอย่าง Simulator ขนาดเล็ก​

บทเรียนนี้ไม่มีตัวอย่าง Simulator เวิร์กโฟลว์นี้วัดความไม่สมบูรณ์ทางกายภาพของอุปกรณ์เฉพาะเครื่องหนึ่ง เช่น คิวบิตของมันผ่อนคลายและเสียเฟสเร็วแค่ไหน และ Gate กับการอ่านค่า (readout) ของมันล้มเหลวบ่อยแค่ไหน Simulator ในอุดมคติไม่มีความไม่สมบูรณ์เหล่านี้เลย จึงไม่มีอะไรให้จำแนกคุณลักษณะ หากคุณแนบโมเดลสัญญาณรบกวนสังเคราะห์ไปกับ fake backend การทดลองก็จะได้เพียงค่าที่คุณใส่เข้าไปในโมเดลกลับคืนมา ด้วยเหตุนี้ บทเรียนนี้จึงไปที่ฮาร์ดแวร์โดยตรง ในสี่ขั้นตอนของ Qiskit pattern

ใช้คุณสมบัติที่รีเฟรชแล้วเพื่อเลือกคิวบิต​

ตัวอย่างเสริมนี้ทำให้เวิร์กโฟลว์สมบูรณ์ โดยตรวจสอบว่าคุณสมบัติที่รีเฟรชแล้วให้ผลลัพธ์ของ Circuit ที่ดีขึ้นหรือไม่ ตัวอย่างจะคอมไพล์ Circuit ชุดเดียวกันสองครั้ง ครั้งหนึ่งด้วยคุณสมบัติที่รายงาน และอีกครั้งด้วยคุณสมบัติที่รีเฟรชแล้ว จากนั้นรันทั้งสองเวอร์ชันและเปรียบเทียบเอาต์พุต ตัวอย่างนี้ใช้ออบเจกต์ backend และ backend_updated จากส่วนก่อนหน้า และส่งงานเพิ่มเติมไปยัง QPU

สร้าง Circuit สำหรับการเปรียบเทียบ​

เตรียมสถานะ Greenberger-Horne-Zeilinger (GHZ) แบบ nnn คิวบิตด้วย Hadamard Gate ตามด้วยห่วงโซ่ของ CNOT Gate แล้ววัดทุกคิวบิต ในอุดมคติ ผลลัพธ์ ∣0⋯0⟩|0\cdots0\rangle∣0⋯0⟩ และ ∣1⋯1⟩|1\cdots1\rangle∣1⋯1⟩ แต่ละอย่างมีความน่าจะเป็น 0.5 เนื่องจากคุณวัดทุกคิวบิต ความผิดพลาดบนคิวบิตใดก็ตามในห่วงโซ่ รวมถึงความผิดพลาดในการอ่านค่า จะลดความน่าจะเป็นของผลลัพธ์ในอุดมคติ ดังนั้นเอาต์พุตที่วัดได้จึงไวต่อคิวบิตกายภาพที่ Transpiler เลือก

คุณสมบัติที่รีเฟรชแล้วมักมีความสำคัญมากที่สุดที่ขนาดปานกลาง ซึ่ง Transpiler สามารถเลือกจากห่วงโซ่คิวบิตที่เป็นตัวเลือกได้หลายแบบ Circuit ที่ใหญ่มากใช้อุปกรณ์เกือบทั้งหมด ทำให้ Transpiler มีที่ว่างน้อยในการหลีกเลี่ยงคิวบิตที่ทำงานได้ไม่ดี เพื่อประหยัดเวลา QPU ให้ลดรายการขนาดของ Circuit ลง

num_qubits_list = list(range(5, 41, 5))
circuits = []
for num_qubits in num_qubits_list:
    circuit = QuantumCircuit(num_qubits)
    circuit.h(0)
    for qubit in range(num_qubits - 1):
        circuit.cx(qubit, qubit + 1)
    circuit.measure_all()
    circuits.append(circuit)

Transpile ด้วยคุณสมบัติที่รายงานและที่รีเฟรชแล้ว​

Transpiler ใช้ Target เพื่อเลือกคิวบิตกายภาพและคำสั่งเนทีฟ หากคุณอัปเดตเฉพาะคุณสมบัติของ Backend target ที่มีอยู่อาจไม่เปลี่ยนแปลง ให้คัดลอก target ดั้งเดิมแทน แล้วนำค่าความผิดพลาดและเวลาโคฮีเรนซ์ที่รีเฟรชแล้วไปใช้กับสำเนาอย่างชัดเจน สำเนานี้คงระยะเวลาของคำสั่งและการเชื่อมต่อเดิมไว้ หากไม่มีเวลาโคฮีเรนซ์สำหรับคิวบิตใด ให้คงค่าเดิมใน target ของคิวบิตนั้นไว้

ค่าความผิดพลาดที่รายงานเป็น 1 หมายความว่าค่าความผิดพลาดไม่ได้นิยามไว้ เพราะการทำ benchmarking ของคิวบิตหรือ Gate นั้นไม่สำเร็จมาหลายวันแล้ว และค่านั้นล้าสมัย (ดู QPU information) ค่านี้ไม่ได้หมายความว่า Gate ใช้งานไม่ได้เสมอไป แต่คุณควรใช้ Gate นั้นด้วยความระมัดระวัง การรันจำแนกคุณลักษณะเพียงครั้งเดียวอาจยังฟิตค่าความผิดพลาดต่ำสำหรับ Gate เช่นนั้นได้ ทำให้ Gate ดูเหมือนเป็นหนึ่งในตัวที่ดีที่สุดบนอุปกรณ์ เพื่อความระมัดระวัง ให้คงรายการเหล่านั้นไว้ที่ค่าที่รายงาน เพื่อให้ Transpiler ยังคงหลีกเลี่ยงรายการเหล่านั้นต่อไป

ใช้ระดับการปรับให้เหมาะสมและ random seed เดียวกันสำหรับการคอมไพล์ทั้งสองครั้ง เพื่อให้การเปรียบเทียบควบคุมความสุ่มของ Transpiler

เปรียบเทียบการแจกแจงเอาต์พุต​

คำนวณ Hellinger fidelity ระหว่างการแจกแจงที่วัดได้แต่ละแบบกับการแจกแจง GHZ ในอุดมคติ ค่า 1 หมายความว่าการแจกแจงตรงกัน เมตริกนี้วัดความสอดคล้องใน computational basis เท่านั้น ไม่ได้วัดโคฮีเรนซ์ระหว่าง ∣0⋯0⟩|0\cdots0\rangle∣0⋯0⟩ และ ∣1⋯1⟩|1\cdots1\rangle∣1⋯1⟩ จึงเป็นขอบบนของ fidelity ของสถานะ GHZ ไม่ใช่หลักฐานยืนยันการพันกัน
