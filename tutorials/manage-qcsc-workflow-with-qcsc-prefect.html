จัดการเวิร์กโฟลว์ quantum-centric supercomputing ด้วย QCSC-Prefect

ประมาณการการใช้งาน: เวลา QPU 30 วินาทีบนโปรเซสเซอร์ IBM Quantum® Heron r2 ค่าประมาณนี้ไม่รวมเวลาในคิวและการประมวลผลแบบคลาสสิก เวลาที่ใช้จริงของคุณอาจแตกต่างไป

ผลลัพธ์การเรียนรู้​

  • ติดตามเวิร์กโฟลว์ quantum-centric supercomputing (QCSC) ใน Prefect Cloud โดยมีหนึ่ง task ต่อหนึ่งขั้นของ Qiskit pattern

  • กำหนดค่าเวิร์กโฟลว์ตามบทบาท โดยพารามิเตอร์การรันอยู่ในฟอร์มการรันของ Prefect Cloud และการตั้งค่า high-performance computing (HPC) และ quantum processing unit (QPU) อยู่ใน Prefect block

  • ทำการรันที่ล้มเหลวต่อโดยไม่ต้องทำซ้ำ QPU job และนำตัวอย่างของการรันหนึ่งกลับมาใช้ในการรันใหม่

สิ่งที่ต้องมีก่อน​

  • ตั้งค่า QCSC-Prefect บน Slurm cluster ซึ่งเตรียม login node ของ Slurm สภาพแวดล้อม Python และข้อมูลรับรองของ IBM Quantum

  • Sample-based quantum diagonalization ของ Hamiltonian ทางเคมี ซึ่งอธิบายอัลกอริทึม

ความเป็นมา​

เวิร์กโฟลว์ QCSC รัน QPU และระบบ HPC เป็นเครื่องเดียว QCSC-Prefect รันเวิร์กโฟลว์ QCSC บน Prefect และทำให้ติดตามได้ กำหนดค่าได้ และทำต่อได้

บทเรียนนี้สาธิตฟีเจอร์เหล่านี้ด้วย sample-based quantum diagonalization (SQD) ของโมเลกุล N2_22​ Quantum Resource Management Interface (QRMI) สุ่มตัวอย่าง circuit ภายใน job ของ Slurm ตัวแก้ eigensolver Fulqrum diagonalize ซับสเปซที่สุ่มได้ใน Slurm job เพิ่มเติม deployment ของ Prefect Cloud หนึ่งตัวรันทั้งสองอย่าง

QCSC-Prefect ยังรันงาน QCSC ขนาดใหญ่ ดังในโปรเจกต์ต่อไปนี้

  • การศึกษาสารเชิงซ้อนโปรตีน-ลิแกนด์ที่มีมากกว่า 12,000 อะตอมใช้ QCSC-Prefect โดยสุ่มตัวอย่างชิ้นส่วน quantum-embedding บนโปรเซสเซอร์ IBM Quantum 156 qubit สองตัว ด้วย qubit สูงสุด 94 ตัว และ diagonalize ซับสเปซของชิ้นส่วนบนซูเปอร์คอมพิวเตอร์ Fugaku, Miyabi-G และ ROQUO [1]

  • การศึกษากลุ่มก้อนเหล็ก-กำมะถันรัน workflow SQD ของ QCSC-Prefect แบบขยายด้วย 36 ออร์บิทัล (72 qubit) และมิติซับสเปซสูงสุด 3×10103 \times 10^{10}3×1010 บนซูเปอร์คอมพิวเตอร์ Fugaku, Miyabi และ ROQUO [2]

ความท้าทายของเวิร์กโฟลว์ QCSC​

เวิร์กโฟลว์ SQD เป็นตัวอย่างทั่วไปของงาน QCSC QCSC-Prefect ตอบแต่ละความท้าทายด้วยหนึ่งฟีเจอร์ ดังตารางต่อไปนี้

ความท้าทายฟีเจอร์ของ QCSC-Prefect
ครอบคลุมหลายทรัพยากร Slurm job หนึ่งตัวถือ QPU จากนั้น Slurm job จำนวนมาก diagonalize ซับสเปซ รอบแล้วรอบเล่าเวิร์กโฟลว์ที่ติดตามได้
มีพารามิเตอร์มากมายในหลายระดับ (วิทยาศาสตร์ circuit และ cluster) และข้อมูลรับรองต้องไม่อยู่ในระดับใดเลยพารามิเตอร์ที่กำหนดค่าได้
ใช้เวลานานและอาจล้มเหลวได้ทุกจุด ไม่ว่าจะจากขีดจำกัด walltime โหนดล่ม หรือคิว QPU ที่ยาว หากไม่ระวัง ความล้มเหลวช่วงท้ายหมายถึงต้องสุ่มตัวอย่างบน QPU ใหม่อีกครั้งการรันที่ทำต่อได้

แต่ละขั้นของ Qiskit Pattern ใน QCSC-Prefect ทีละขั้น จบด้วยกล่องที่แสดงว่า QCSC-Prefect ติดตาม กำหนดค่า และทำต่อขั้นนั้นอย่างไร

เวิร์กโฟลว์ที่ติดตามได้​

Prefect flow คือฟังก์ชัน Python ที่ประกอบด้วย task QCSC-Prefect ทำให้แต่ละขั้นของ Qiskit pattern (Map, Optimize, Execute และ Postprocess) เป็นหนึ่ง task สำหรับทุกการรัน Prefect Cloud แสดงข้อมูลต่อไปนี้

  • กราฟ task พร้อมลูกศรทุกจุดที่ task หนึ่งส่งผลลัพธ์ให้อีก task หนึ่ง

  • สถานะ อินพุต log และระยะเวลาของแต่ละ task ซึ่งกรองได้ด้วยแท็กขั้นตอน map, optimize, execute และ post-process

  • artifact ซึ่งเป็นตารางและลิงก์ที่ task เผยแพร่ เช่นแหล่งที่มาของตัวอย่างหรือพลังงานของแต่ละซับสเปซ

โฮสต์ของเวิร์กโฟลว์ทำหน้าที่ส่งและตรวจสอบงานเท่านั้น งานที่ใช้การคำนวณสูงรันเป็น Slurm job ดังภาพต่อไปนี้

พารามิเตอร์ที่กำหนดค่าได้​

QCSC-Prefect เก็บการตั้งค่าแต่ละชนิดไว้ในที่ของมันเอง ดังตารางต่อไปนี้

ชนิดตัวอย่างการเปลี่ยนแปลงที่เก็บ
พารามิเตอร์การรันโมเลกุล shot มิติซับสเปซทุกการรันฟอร์มการรันของ Prefect Cloud จัดกลุ่มตามขั้น
Blockพาร์ทิชัน walltime เธรด พาธของไฟล์ที่รันได้ ทรัพยากร QPUต่อ clusterPrefect block สร้างครั้งเดียว
ข้อมูลรับรองPrefect API key, IBM Quantum API keyนานๆ ครั้งการล็อกอิน Prefect Cloud บนโฮสต์ของเวิร์กโฟลว์ และ QRMI (qcsc-qrmi login) บน cluster ซึ่งตั้งค่าทั้งคู่ในคู่มือการตั้งค่า

Block อธิบายแต่ละ job ในสามชั้นของตารางต่อไปนี้

Blockระบุเนื้อหา
CommandBlockอะไรที่รันไฟล์ที่รันได้และอาร์กิวเมนต์เริ่มต้น
ExecutionProfileBlockรันอย่างไรโหนด เธรด walltime launcher โมดูล และสภาพแวดล้อม

flow โหลด block ตามชื่อเมื่อรัน ดังนั้นการเปลี่ยน block จึงไม่กระทบ flow และพารามิเตอร์การรัน

การรันที่ทำต่อได้​

Prefect เก็บผลลัพธ์ของสามขั้นแรกไว้กับการรัน flow ถ้า task ภายหลังล้มเหลว Retry บนการรัน flow จะใช้ผลลัพธ์ที่เก็บไว้ซ้ำและรันเฉพาะส่วนที่ล้มเหลว ดังภาพต่อไปนี้

การรันใหม่ยังโหลดตัวอย่างของการรันก่อนหน้าแทนการสุ่มตัวอย่างได้ เพราะขั้น Execute บันทึกว่าตัวอย่างอยู่ที่ใด

SQD โดยสังเขป​

SQD สุ่มตัวอย่าง bitstring จาก circuit local unitary cluster Jastrow (LUCJ) ที่สร้างจากแอมพลิจูด coupled cluster singles and doubles (CCSD) แก้ bitstring ที่ถูกสัญญาณรบกวนทำให้เสียหาย (configuration recovery) และ diagonalize Hamiltonian ในซับสเปซที่ขึงด้วยคอนฟิกูเรชันที่สุ่มได้ [3] บทเรียน SQD อธิบายอัลกอริทึม ใน QCSC-Prefect SQD คือ flow sqd ซึ่งมีกราฟ task ดังต่อไปนี้

ขั้นTaskอินพุตจาก task อื่น
Mapcompute_molecular_integralsไม่มี
Optimizeget_lucj_paramsIntegral จาก Map
Executequantum_sampling โดยมี build_lucj_circuit อยู่ภายในพารามิเตอร์ LUCJ จาก Optimize
Postprocesssqd_loopIntegral จาก Map และตัวอย่างจาก Execute

เมื่อการรันนำตัวอย่างกลับมาใช้ load_qrmi_result (หรือ load_runtime_job สำหรับตัวอย่างจาก IBM Quantum Platform) จะแทนที่ทั้ง get_lucj_params และ quantum_sampling การรันจึงไม่มี task Optimize ในโหมด random (Quantum Source ตั้งเป็น random) จะไม่มี task Optimize หรือ Execute และ Map ป้อนให้ sqd_loop โดยตรง

หมายเหตุ

เวิร์กโฟลว์ QCSC-Prefect รันบน cluster ที่จัดการด้วย Slurm ไม่ใช่ใน notebook นี้ ก่อนรัน ให้ทำตั้งค่า QCSC-Prefect บน Slurm cluster ให้เสร็จ ซึ่งให้สิ่งต่อไปนี้

  • checkout ของ QCSC-Prefect ที่ $QCSC_PREFECT (~/qcsc-prefect) และไดเรกทอรีทำงานที่ $QCSC_WORK_DIR (/shared/work/qcsc-prefect) ทั้งสองอยู่บนที่เก็บข้อมูลที่โหนดประมวลผลใช้ร่วมกัน

  • บน login node ของ Slurm ซึ่งคือโฮสต์ของเวิร์กโฟลว์ มีสภาพแวดล้อม ~/venv/qcsc-host พร้อมแพ็กเกจ QCSC-Prefect และการล็อกอิน Prefect Cloud

  • ข้อมูลรับรองของ IBM Quantum ที่เก็บด้วย qcsc-qrmi login และ block qrmi-runtime บน cluster ที่มี QRMI และ SPANK plugin ของมัน

  • บนโหนดประมวลผล มีสภาพแวดล้อม ~/venv/qcsc-node พร้อม QRMI, task_runner ของมัน และ qcsc-prefect-qiskit

รันขั้นตอนต่อไปนี้หนึ่งครั้ง แต่ละขั้นระบุโหนดที่มันรัน

ติดตั้งเวิร์กโฟลว์ SQD บนโฮสต์ของเวิร์กโฟลว์​

ตั้งค่าตัวแปรของคู่มือการตั้งค่า เปิดใช้งาน ~/venv/qcsc-host และติดตั้งเวิร์กโฟลว์ SQD และการผสาน Fulqrum

# Run in a terminal on the workflow host.
# Optional if your ~/.bashrc sets the two variables
export QCSC_PREFECT="$HOME/qcsc-prefect"
export QCSC_WORK_DIR="/shared/work/qcsc-prefect"

source ~/venv/qcsc-host/bin/activate
cd "$QCSC_PREFECT"
uv pip install --no-deps -e packages/qcsc-prefect-fulqrum
uv pip install -e algorithms/qcsc_workflow_utility
uv pip install -e algorithms/open_loop/sqd
which sqd-create-blocks sqd-deploy

ติดตั้งตัวแก้ Fulqrum บนโหนดประมวลผล​

เปิด shell บนโหนดประมวลผล srun ส่งตัวแปรของ shell บนโฮสต์ของเวิร์กโฟลว์ไปยังโหนดประมวลผล

# Run in a terminal on the workflow host.
srun -N1 --pty bash

QRMI worker ทรานสไพล์ circuit บนโหนดประมวลผลด้วย SQD transpilation hook ซึ่ง import เฉพาะ Qiskit เพิ่ม hook ลงใน ~/venv/qcsc-node และตรวจสอบ import คำสั่ง python ไม่พิมพ์อะไรเมื่อ import สำเร็จ

# Run in the shell on the compute node.
source ~/venv/qcsc-node/bin/activate
cd "$QCSC_PREFECT"
uv pip install --no-deps -e algorithms/open_loop/sqd
python -c "import qrmi, qcsc_prefect.integrations.qiskit.qrmi.worker, sqd_common.transpile"

สร้าง Fulqrum และ qcsc-fulqrum-solve ในสภาพแวดล้อมของมันเอง packages/qcsc-prefect-fulqrum/native/fulqrum การสร้างต้องใช้ตัวคอมไพล์ C++ ที่มี OpenMP FULQRUM_WITH_PRIMME=1 ยังสร้าง eigensolver PRIMME ซึ่งต้องใช้ตัวคอมไพล์ C, Python header, pkg-config และไลบรารี BLAS และ LAPACK ที่มีไฟล์ .pc

# Run in the shell on the compute node.
cd "$QCSC_PREFECT"
FULQRUM_WITH_PRIMME=1 bash packages/qcsc-prefect-fulqrum/native/build_fulqrum.sh

ขั้นที่ 1: แมปอินพุตแบบคลาสสิกเป็นปัญหาควอนตัม​

stage Map ซึ่งคือ task compute_molecular_integrals ใน workflow แปลงโมเลกุลเป็นอินพุตของทุก stage ถัดไป Restricted Hartree-Fock (RHF) ให้ molecular orbital และ active-space integral ตัด core 1s ที่ถูก freeze สองตัวออก CCSD ให้แอมพลิจูด t2t_2t2​ ของ ansatz และ density matrix ของมันให้ orbital occupancy ที่ใช้เริ่ม configuration recovery CCSD วน CCSD_MAXITER รอบ โดยแต่ละรอบเริ่มจากแอมพลิจูดก่อนหน้า ผลลัพธ์จึงไม่ขึ้นกับประวัติ DIIS ของรอบแรก notebook นี้ใช้ 4 รอบ และ workflow ใช้ 10 รอบ

ATOM = "N 0 0 0; N 0 0 1.1"
BASIS = "6-31g"
N_FROZEN = 2
CCSD_MAXITER = 4

mol = pyscf.gto.M(atom=ATOM, basis=BASIS, symmetry=False, verbose=0)
mf = scf.RHF(mol).run()
norb = mol.nao_nr() - N_FROZEN
nelec = (mol.nelec[0] - N_FROZEN, mol.nelec[1] - N_FROZEN)

# Active-space Hamiltonian with the 1s cores frozen
cas = mcscf.CASCI(mf, ncas=norb, nelecas=nelec)
one_body_tensor, core_energy = cas.get_h1eff()
two_body_tensor = ao2mo.restore(1, cas.get_h2eff(), norb)

# CCSD, iterated from the previous amplitudes
ccsd = cc.CCSD(mf, frozen=N_FROZEN)
eris = ccsd.ao2mo()
ccsd.kernel(eris=eris)
for _ in range(CCSD_MAXITER - 1):
    ccsd.kernel(ccsd.t1, ccsd.t2, eris=eris)
t2 = ccsd.t2

occupancies = np.diag(ccsd.make_rdm1())[N_FROZEN:] / 2
initial_occupancies = (occupancies, occupancies)

print(f"norb = {norb}, nelec = {nelec}")
print(f"E(RHF)  = {mf.e_tot:.8f} Ha")
print(f"E(CCSD) = {ccsd.e_tot:.8f} Ha")

        round_energies.append(
            min(result.energy for result in results) + core_energy
        )
        print(
            f"{label}, round {len(round_energies)}: {round_energies[-1]:.8f} Ha"

    result = diagonalize_fermionic_hamiltonian(

        callback=callback,
        seed=np.random.default_rng(24),
    )

Retry การรันที่ล้มเหลวและนำตัวอย่างกลับมาใช้​

Retry: สมมติว่าในการรันที่ตั้ง Max Iteration เป็น 10 solver job ชน walltime ในรอบที่ 5 และ sqd_loop ล้มเหลว ให้เพิ่ม walltime ใน block exec-sqd-fulqrum-slurm ใต้ Blocks แล้วเลือก Retry บน flow run ที่ล้มเหลว การรันที่ retry จะโหลดผลลัพธ์ที่เก็บไว้ของสาม stage แรกและไม่ส่ง QPU job มันรันเฉพาะ sqd_loop อีกครั้งด้วย walltime ใหม่ และเริ่มที่รอบ 5 จาก checkpoint ของรอบ 4 log ของมันแสดง [ckpt] RESUME from …: completed 4 step(s) แล้วตามด้วย SQD iteration 5/10 ดังภาพต่อไปนี้

Reuse: การรันใหม่จะคำนวณทุกอย่างอีกครั้ง เว้นแต่คุณชี้ไปยังตัวอย่างก่อนหน้า หากต้องการลอง subspace dimension อื่นด้วยตัวอย่างเดิม ให้เริ่ม custom run ด้วยพารามิเตอร์เดิม ตั้ง Load from QRMI Job Directory (qrmi_result_dir) เป็น work directory ใน artifact sqd-sampling-source ของการรันแรก และเปลี่ยน Subspace Dimension การรันใหม่จะแทน get_lucj_params และ quantum_sampling ด้วย load_qrmi_result ซึ่งอ่านตัวอย่างและไม่ส่งอะไรไปที่ QPU Reset Mitigation ใน sqd-advanced-settings ต้องตรงกับการรันแรก เพราะการโหลดซ้ำจะนำมาใช้ สำหรับตัวอย่างที่เก็บผ่าน IQP ให้ตั้ง Load from Qiskit Runtime Job ID (qiskit_runtime_job_id) แทน และ stage จะเป็น load_runtime_job มันอ่าน job ด้วยข้อมูลรับรองของ block QuantumRuntime ของ prefect-qiskit ที่ระบุใน Quantum Runtime Block (reload) (ibm-runner เป็นค่าเริ่มต้น) สร้าง block นั้นครั้งเดียวด้วย prefect block create quantum-runtime

ทำ recovery ต่อด้วยรอบที่มากขึ้น: เริ่ม custom run ด้วยพารามิเตอร์เดิม ตั้ง Resume from Checkpoint (resume_checkpoint) เป็น path ใน artifact sqd-checkpoint ของการรันแรก และเพิ่ม Max Iteration การรันใหม่จะทำต่อหลังรอบที่เสร็จแล้ว จาก occupancy และพลังงานที่ดีที่สุดที่เก็บไว้ ตัวอย่างเช่น checkpoint ที่เสร็จ 32 จาก 100 รอบ และ Max Iteration ตั้งเป็น 200 จะทำต่อที่รอบ 33/200 การรันใหม่อ่าน checkpoint นั้นและเขียนของตัวเอง และมีกฎดังต่อไปนี้

  • ตัวอย่าง โมเลกุล Subspace Dimension Batch Number และชนิดของ solver (ส่วน fulqrum_solver_job ของ solver block) ต้องตรงกับการรันแรก จึงให้นำตัวอย่างของมันกลับมาใช้ ดังใน Reuse

  • ชื่อและการตั้งค่า job ของ solver block เช่น walltime สามารถเปลี่ยนได้

  • หากการตั้งค่าที่ต้องตรงกันต่างกัน การรันจะล้มเหลวก่อน solver job ใด ๆ และระบุความต่างนั้น
