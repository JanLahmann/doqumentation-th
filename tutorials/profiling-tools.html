เครื่องมือสำหรับทำโปรไฟล์ ปรับแต่ง และตรวจสอบการทดลอง

ประมาณการการใช้งาน: 10 นาทีบนโปรเซสเซอร์ Heron r2 (หมายเหตุ: เป็นเพียงค่าประมาณ เวลารันจริงของคุณอาจต่างออกไป)

การจะได้ผลลัพธ์ที่ดีจากคอมพิวเตอร์ควอนตัม คุณต้องการมากกว่าวงจรที่ออกแบบมาดี สภาพปัจจุบันของอุปกรณ์ วิธีที่วงจรของคุณถูกจัดตาราง noise ที่วงจรได้รับ รวมถึงเวลาและวิธีที่งานของคุณรันบนหน่วยประมวลผลควอนตัม (QPU) ล้วนส่งผลต่อคุณภาพของผลลัพธ์ Qiskit และ IBM Quantum® Compute Service มีชุดเครื่องมือสำหรับนักพัฒนาที่เพิ่มขึ้นเรื่อย ๆ ซึ่งเปิดเผยข้อมูลนี้ คุณสามารถใช้เครื่องมือเหล่านี้เพื่อดำเนินการตามข้อมูลนั้นก่อนที่จะใช้เวลา QPU กับการทดลองเต็มรูปแบบ และเพื่อดีบักการทดลองที่เสร็จแล้ว

บทแนะนำนี้ใช้การทดลองแบบครบวงจรหนึ่งชุดเพื่อแสดงวิธีผสานเครื่องมือเหล่านี้ในแต่ละขั้นของเวิร์กโฟลว์การพัฒนาทั่วไป เครื่องมือบางตัวไม่ได้มีประโยชน์กับทุกการทดลอง ดังนั้นให้เลือกเครื่องมือที่ตอบคำถามที่คุณมีเกี่ยวกับงานของคุณเอง

เวิร์กโฟลว์มีดังนี้:

  1. เตรียม mirror circuit ของการวิวัฒนาการตามเวลาแบบ Trotter ของโมเดล Ising สนามขวางแบบเชิงเส้น

  2. เลือก backend ที่มีชุดข้อมูลการสอบเทียบทางเลือกซึ่งออกแบบมาสำหรับวิธีลดข้อผิดพลาดที่อิงโมเดล noise

  3. รันการทดลอง benchmark อุปกรณ์ เพื่อให้ transpiler ใช้คุณสมบัติอุปกรณ์ที่ทันสมัยเมื่อเลือก layout

  4. ตรวจสอบข้อมูลเวลาของวงจรที่จัดตารางแล้ว

  5. เรียนรู้โมเดล noise แบบ Pauli-Lindblad และ readout สำหรับวงจร

  6. รันการจำลองในเครื่องแบบไม่มี noise แบบไม่ทำ mitigation และแบบทำ mitigation การจำลองที่มี noise ใช้โมเดล noise ที่เรียนรู้มาเพื่อแสดงว่าวิธีลดข้อผิดพลาดที่เลือกอาจช่วยปรับปรุงได้มากแค่ไหน บทแนะนำนี้ใช้ probabilistic error cancellation (PEC) และ Twirled Readout Error eXtinction (TREX)

  7. รับค่าประมาณการการใช้งานโดยไม่ต้องรันบน QPU เพื่อตรวจสอบว่าคุณต้องปรับการทดลองให้พอดีกับงบประมาณหรือไม่

  8. เริ่ม session และสั่งการสอบเทียบ เพื่อให้การทดลองใช้ข้อมูลการสอบเทียบล่าสุด

  9. รันการทดลองบน QPU โดยใช้ Estimator และเปรียบเทียบผลจากฮาร์ดแวร์กับตัวอย่างที่จำลองไว้

  10. ตรวจสอบ execution span เพื่อดูว่ามีช่องว่างขนาดใหญ่ระหว่างกลุ่มของการทำงาน (chunk) หรือไม่

ขั้นตอนที่ 1: ระบุวงจรและ observable​

เตรียม mirror circuit ของการวิวัฒนาการตามเวลาแบบ Trotter ของโมเดล Ising สนามขวางแบบเชิงเส้น สะท้อนวงจรเพื่อหักล้าง unitary ของวงจรและได้วงจร identity เนื่องจากผลลัพธ์ในอุดมคติคือสถานะศูนย์ทั้งหมด ค่าคาดหวังในอุดมคติของ observable ZZZ ของแต่ละคิวบิตเดี่ยวจึงเป็น 1 การสะท้อนยังทำให้ความลึกของวงจรเพิ่มเป็นสองเท่า ซึ่งขยายผลของ noise

import numpy as np
from qiskit.circuit import QuantumCircuit
from qiskit.quantum_info import SparsePauliOp

def construct_ising_circuit(
    num_qubits: int,
    num_trotter_steps: int,
    rx_angle: float,
    barrier: bool = True,
) -> QuantumCircuit:
    circuit = QuantumCircuit(num_qubits)

    for _step in range(num_trotter_steps):
        circuit.rx(rx_angle, range(num_qubits))
        if barrier:
            circuit.barrier()
        for first_qubit in (1, 2):
            for idx in range(first_qubit, num_qubits, 2):
                # equivalent to Rzz(-pi/2):
                circuit.sdg([idx - 1, idx])
                circuit.cz(idx - 1, idx)
        if barrier:
            circuit.barrier()

    return circuit

def mirror_circuit(circuit: QuantumCircuit) -> QuantumCircuit:
    mirror_circ = circuit.copy_empty_like()
    mirror_circ.compose(circuit, inplace=True)
    mirror_circ.barrier()
    mirror_circ.compose(circuit.inverse(), inplace=True)
    mirror_circ.measure_active()
    return mirror_circ
num_qubits = 20
observables = [
    SparsePauliOp("I" * ((num_qubits - 1) - q) + "Z" + "I" * q)
    for q in range(num_qubits)
]

# Free parameters of the demonstration circuit: the number of Trotter steps
# sets the circuit depth, and rx_angle is the transverse-field rotation angle
# applied in each step (pi/4 makes the dynamics non-Clifford)
num_trotter_steps = 5
rx_angle = np.pi / 4

circuit = construct_ising_circuit(
    num_qubits, num_trotter_steps, rx_angle, barrier=False
)
mirrored_circuit = mirror_circuit(circuit)
mirrored_circuit.draw(
    "mpl", fold=-1, scale=0.3, idle_wires=False, measure_arrows=False
)

2.1 ใช้การสอบเทียบทางเลือกถ้าเหมาะสม​

IBM® สอบเทียบ QPU ของตนเป็นระยะเพื่อให้ประสิทธิภาพดีในการใช้งานทั่วไป อย่างไรก็ตาม บางงานได้ประโยชน์จาก instruction ที่ปรับพารามิเตอร์ต่างออกไป สำหรับข้อมูลเพิ่มเติม ดู Specially calibrated instructions

บทแนะนำนี้ใช้ชุดข้อมูลการสอบเทียบทางเลือกชื่อ slow_gates_ac การสอบเทียบนี้มี cz gate ที่ช้าลง และมอดูเลต bias ของระบบสองระดับ (TLS) เพื่อให้ข้อผิดพลาดของอุปกรณ์เสถียรตลอดเวลา การเปลี่ยนแปลงเหล่านี้เป็นประโยชน์ต่อวิธีลดข้อผิดพลาดที่พึ่งพาโมเดล noise ที่เรียนรู้มา การสอบเทียบ slow_gates_ac ใช้ได้เฉพาะบน Heron QPU หากคุณรันบน Nighthawk QPU ให้ใช้ slow_gates แทน

2.2 รัน benchmark อุปกรณ์แบบเรียลไทม์​

หนึ่งในขั้นตอนที่สำคัญที่สุดของการ transpile คือการเลือก layout ซึ่งแมปคิวบิตเสมือนในวงจรไปยังคิวบิตจริงบนอุปกรณ์เป้าหมาย layout ที่ดีทำให้จำนวนการดำเนินการ SWAP ที่ต้องใช้น้อยที่สุด และวางวงจรบนคิวบิตที่ทำงานได้ดีที่สุด ดังนั้นคุณภาพของ layout เริ่มต้นจึงส่งผลต่อคุณภาพของผลลัพธ์ได้อย่างมาก

ชุดรูทีน benchmark เป็นระยะรันบน IBM QPU ทุกตัวเพื่อรายงานประสิทธิภาพปัจจุบันของคิวบิต: เวลา relaxation (T1T_1T1​), เวลา coherence (T2T_2T2​), readout error และข้อผิดพลาดของ gate หนึ่งและสองคิวบิต Qiskit transpiler ใช้ตัวชี้วัดเหล่านี้ระหว่างการเลือก layout

อย่างไรก็ตาม คุณสมบัติของคิวบิตตัวนำยิ่งยวดอาจดริฟต์ในช่วงเวลาที่สั้นกว่านั้น และความบกพร่องชั่วคราวที่เรียกว่า TLS อาจทำให้คิวบิตที่ทำงานได้ดีตอนสอบเทียบเสื่อมลงชั่วคราว ถ้า transpiler ใช้ข้อมูลที่ล้าสมัย มันก็เลือก layout ที่ดีที่สุดไม่ได้ ดังนั้นการใช้เวลา QPU บางส่วนเพื่อหาลักษณะเฉพาะของอุปกรณ์ก่อนเลือก layout จึงอาจคุ้มค่า

ดูรายละเอียดทีละขั้นได้ที่บทแนะนำ Refresh backend properties with real-time benchmarking ชุดการหาลักษณะเฉพาะสร้างการทดลองหลายชุด ส่งหลายงาน และฟิตผลลัพธ์ กระบวนการนี้อาจใช้เวลารวมไม่กี่นาที เปิดการบันทึก log ระดับ INFO เพื่อให้แต่ละขั้นพิมพ์ความคืบหน้าขณะรัน

import sys

logger = logging.getLogger("qiskit_device_benchmarking")

3.2 ใช้ PEC กับ TREX​

การเลือกวิธี error mitigation ที่สมดุลระหว่างต้นทุนและความแม่นยำสำหรับการทดลองเฉพาะของคุณอาจทำได้ยาก คุณสามารถใช้ AI agent skill ชื่อ select-error-mitigation เพื่อวิเคราะห์วิธีที่มีให้สำหรับ workload ของคุณ skill นี้จะแสดงรายงานสรุปที่อธิบายว่าแต่ละวิธีถูกเลือกหรือไม่ และเพราะเหตุใด

ดูข้อมูลเพิ่มเติมที่ GitHub repository Qiskit AI skills บทเรียนนี้ใช้ PEC กับ TREX โดยตรง เพื่อให้คุณทำตามได้โดยไม่ต้องใช้ AI agent

PEC เป็นเทคนิคที่ลด quantum noise เมื่อคุณคำนวณค่าคาดหวังของ observable ภายใต้เงื่อนไขอุดมคติ PEC สามารถให้ค่าประมาณที่ไม่เอนเอียงของค่าคาดหวังได้ โดยเรียนรู้ noise ของแต่ละชั้นของ two-qubit gate จากนั้นรันชุดของ circuit ที่โดยเฉลี่ยแล้วใช้ตัวผกผันของ noise นั้น PEC ใช้ Pauli twirling เพื่อปรับ noise ให้เป็น Pauli channel ซึ่งเรียนรู้และผกผันได้อย่างมีประสิทธิภาพ

ในทางปฏิบัติ PEC แม่นยำเท่ากับ noise model ที่เรียนรู้มาเท่านั้น โมเดล sparse Pauli-Lindblad รวมเฉพาะ error term แบบ one-qubit และ two-qubit บน qubit ที่อยู่ติดกัน จึงไม่สามารถจับผลกระทบอย่าง crosstalk ระหว่าง qubit ที่อยู่ห่างกัน หรือ error ที่สัมพันธ์กันตามเวลาได้อย่างสมบูรณ์ noise ของอุปกรณ์ยังอาจเปลี่ยนแปลง (drift) ระหว่างการเรียนรู้ noise และการรันจริง PEC ไม่ลบ noise ที่โมเดลมองไม่เห็น และจะชดเชยมากเกินไปสำหรับ noise ที่โมเดลประเมินสูงเกินจริง ดังนั้นผลลัพธ์ที่ผ่านการ mitigate แล้วอาจยังเบี่ยงเบนจากค่าอุดมคติได้ทั้งสองทิศทาง

TREX เป็นเทคนิคที่ลด measurement error และมีประโยชน์เมื่อคุณประมาณค่าคาดหวังของ Pauli observable โดยอาศัย measurement twirling ซึ่งทำให้ readout-error transfer matrix เป็นเมทริกซ์แนวทแยงและผกผันได้ง่าย TREX เรียนรู้ค่าปรับสเกลจาก diagonal noise channel โดยวัด calibration circuit ที่ผ่านการ twirl และเริ่มต้นในสถานะศูนย์ คุณสามารถเปิดใช้ทั้ง PEC และ TREX ได้โดยตั้งค่าตัวเลือกของ Estimator บทเรียนนี้ใช้การ implement ฝั่ง client ของอินเทอร์เฟซ SamplerV2 และ EstimatorV2 ของ Qiskit ซึ่งเริ่มมีใน qiskit-ibm-runtime v0.50.0 primitive ฝั่ง client เหล่านี้ทำการประมวลผลก่อนและหลังส่วนใหญ่ในเครื่อง และมอบหมายการรันให้ primitive Executor เมื่อ primitive รันฝั่ง client คุณจะได้ความโปร่งใสมากขึ้น ได้รับ feedback ที่เร็วขึ้นเมื่อ debug และควบคุมได้ละเอียดขึ้น

เมื่อคุณส่ง circuit ที่มีหลายการตั้งค่า เช่นเมื่อใช้ gate twirling IBM Quantum Compute Service ไม่จำเป็นต้องรันการตั้งค่า circuit ทั้งหมดพร้อมกัน แต่จะจัดกลุ่มเป็น chunk และรันหนึ่ง chunk ต่อหนึ่ง shot loop โดย shot loop คือการรันหนึ่งรอบบนฮาร์ดแวร์ควอนตัม ซึ่ง circuit ทุกตัวใน chunk จะถูกรันตามจำนวน shot ที่ร้องขอ

job ทั้งหมดที่ส่งไปยัง QPU จริงต้องมีการประมวลผลแบบคลาสสิกก่อนรันบางส่วน เช่น การแปลงเป็น pulse ที่ส่งไปยังฮาร์ดแวร์ได้ เนื่องจากการประมวลผลก่อนรันนี้ทำแบบขนานได้ บริการจึงนำ job ออกจากคิวและเริ่มหลายงานพร้อมกัน แต่ QPU ประมวลผลได้ครั้งละหนึ่งหน่วยงานเท่านั้น ดังนั้นหาก job ของคุณสร้างหลาย chunk มันอาจถูกสลับกับ chunk ของ job ผู้ใช้อื่น และแต่ละ chunk อาจต้องรอคิวบน QPU

metadata ของผลลัพธ์ job รายงาน timing การรันบน QPU ของแต่ละ chunk การแสดงภาพต่อไปนี้แสดงว่ามีช่องว่างขนาดใหญ่ระหว่างการรัน chunk ใน job ของคุณหรือไม่ หากช่องว่างกว้างเกินกว่าที่การทดลองของคุณทนได้ คุณอาจต้องรัน job ซ้ำ หรือใช้ session execution mode ซึ่งให้ workload ของคุณเข้าถึง QPU แบบเอกชน

  • รันการทดลองซ้ำทั้งแบบมีและไม่มี calibration slow_gates_ac (ขั้นตอน 2.1), คุณสมบัติอุปกรณ์ที่อัปเดตแล้ว (ขั้นตอน 2.2) หรือ session calibration (ขั้นตอน 4.1) เพื่อวัดว่าแต่ละเครื่องมือปรับปรุงผลลัพธ์ของ workload คุณได้มากเพียงใด

  • เรียนรู้เพิ่มเติมเกี่ยวกับ primitive ฝั่ง client และ Executor ใน Migrate from server-side to client-side Sampler and Estimator
